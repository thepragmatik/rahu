Decision records

Eight accepted decisions that explain why the system looks the way it does, and what was deliberately left out. Each one records the alternatives that were considered, because a decision without a rejected alternative is not yet a decision.

01How to read these

Each record has three parts: the problem, the decision, and what the decision costs. The third part is the one that matters most, because a decision with no recorded downside has usually not been examined.

Expand any record below. All eight are accepted.

02The eight records

0001Own the agent loop Accepted

The problem

General agent frameworks control their own lifecycle, which hides exactly the routing boundaries, continuation handling and budget decisions this project exists to test.

The decision

A small bounded loop in ordinary Java, with narrow ports for decisions, generation, tools and observations. Libraries may parse JSON and speak HTTP; none of them controls the loop.

What it costs

Loses the ecosystem features a framework would have provided. Accepted: inspectability is the research variable here.

Read ADR 0001

0002A genuine System One decision plane Accepted

The problem

Decision models answer bounded questions well and generate prose badly. Model confidence is neither permission nor evidence of a correct answer.

The decision

Typed HTTP decisions for classification, routing, advisory tool relevance and compaction policy. Generation models write answers, summaries and tool arguments. Java owns feasibility, validation, budgets and authority.

What it costs

A real decision service becomes an operational dependency. Accepted: a fake labelled as the real thing would defeat the research question.

Read ADR 0002

0003Joint execution candidates Accepted

The problem

Choosing a model and an effort independently can produce combinations the provider does not support. Omitting a configuration value is not the same as disabling reasoning.

The decision

Java builds the legal tuples from configured pools and capability evidence. The decision service chooses a stable candidate ID. Provider default, disabled reasoning and explicit effort are three separate policies.

What it costs

The candidate set must be built before the decision is asked, which costs a round of local work per turn. Accepted: an impossible pair costs a paid rejection.

Read ADR 0003

0004Java 27 with preview features Accepted

The problem

The owner asked for the latest Java and permits preview features where they improve a concrete design.

The decision

Pin the verified working distribution. Use records, sealed outcomes, pattern switches, virtual threads and structured concurrency where the semantics fit, and enable preview consistently in compilation, tests, launcher and packaging.

What it costs

Preview features can change between releases, so the build is pinned to a verified release rather than a moving target.

Read ADR 0004

0005Traces and policy replay Accepted

The problem

Routing decisions and failures must be observable. Event-sourcing the whole runtime would promise deterministic model regeneration, which cannot be delivered.

The decision

Append schema-versioned JSONL from an ordinary in-memory state machine. Metadata capture is default; payload capture is explicit. Replay is deterministic only with frozen inputs and recorded outcomes.

What it costs

Gives up the ability to reconstruct state from the log alone. Accepted: the alternative would have produced a false guarantee.

Read ADR 0005

0006Strict configuration and shadow-first routing Accepted

The problem

Silent model selection creates surprise cost and quality. Provider aliases and capability data change often, so a baked-in list rots.

The decision

Strict JSON against a generated schema, a closed key set, explicit model pools, and shadow mode as the default: the decision service proposes, and the configured baseline runs.

What it costs

Shadow mode doubles decision cost while it is on. Accepted: the alternative is changing routing with no measurement.

Read ADR 0006

0007Seven subsystems, four modules Accepted

The problem

A single autonomous build should reach a usable harness. The earlier handoff allowed stopping at the first slice and left several contracts implicit.

The decision

Require explicit coverage of all seven harness areas, with a minimal implementation or a deliberate absence. Keep four modules, read-only tools, no dynamic plugins, no cross-process recovery and no sub-agents.

What it costs

One agent cannot claim orchestration design. Accepted: an honest single-agent position is worth more than an untested delegation claim.

Read ADR 0007

0008Strict outbound privacy admission Accepted

The problem

Excluding secrets from logs does not stop disclosure through classification, summaries, tool observations or adapter fields. Sending raw content to a privacy classifier has already disclosed it.

The decision

Deterministic local classification before admission and again on the exact serialised body before transport. Unknown or restricted content fails closed. Explicit classification cannot override a known protected-data finding.

What it costs

Detection is imperfect, so uncertainty blocks rather than passes. The release report states this limit rather than claiming universal detection.

Read ADR 0008

03Deliberately deferred

These are not gaps. Each was considered and deferred for a stated reason, and none has a placeholder abstraction waiting for it.

Streaming

Non-streaming generation is enough for a review assistant. Streaming adds partial-output states to every error path.

Effectful tools

Read-only tools mean a prompt injection cannot cause damage. That property is worth more than convenience.

Durable resume

Needs a persistent tool journal and a recovery protocol, plus a reason to want either.

Vector memory

In-process ordered history is enough for follow-up questions in one session.

Runtime plugins and MCP

Needs separate trust and permission semantics that the current authority path does not model.

Multi-agent

Needs a strong single-agent baseline and shared budget semantics before delegation means anything.

The rule behind the list

No abstraction is pre-created for a hypothetical future system. An interface with one implementation and no substitution boundary is decoration, and it hides the cost of the real design.
